# Pragmatic Engineering and Software Craftsmanship

Here’s a practical way to think about both.

## The pragmatic engineer

A pragmatic engineer focuses on **delivering value effectively in the real world**. The core idea is not “do the theoretically best thing,” but “do the best thing for this situation.”

### Main principles
- **Solve the actual problem**
  - Don’t optimize for hypothetical future problems before they exist.
  - Build what is needed now, with enough flexibility for likely change.

- **Prefer simple, working solutions**
  - Simplicity reduces bugs, maintenance cost, and coordination overhead.
  - “Simple” means understandable and maintainable, not simplistic.

- **Trade off carefully**
  - Good engineering is about balancing speed, quality, cost, risk, and maintainability.
  - There is rarely a perfect answer, only a best tradeoff.

- **Bias toward shipping**
  - A useful imperfect solution often beats a perfect unreleased one.
  - Learn from real usage rather than speculation.

- **Use judgment, not dogma**
  - Patterns, practices, and “best practices” are tools, not laws.
  - Choose based on context.

- **Avoid premature optimization**
  - Don’t add complexity unless there’s evidence it’s needed.
  - Measure first, optimize second.

- **Be opinionated when it helps**
  - Clear conventions reduce confusion and decision fatigue.
  - Standardize common paths, allow exceptions where needed.

- **Own outcomes**
  - Pragmatic engineers care about user impact, not just code completion.
  - They think in terms of reliability, performance, operations, and support.

## Software craftsmanship

Software craftsmanship is about treating software development as a **discipline of skill, care, and continuous improvement**. The emphasis is on quality, professionalism, and pride in the work.

### Main principles
- **Take pride in your work**
  - Write code you’d be willing to maintain later.
  - Aim for clarity, correctness, and elegance where it matters.

- **Continuous learning**
  - Improve technical skills, design sense, debugging, testing, and communication.
  - Mastery comes from deliberate practice.

- **Sustainability**
  - Build software that can be maintained by yourself and others over time.
  - Favor readable code, good tests, and clean boundaries.

- **Refactoring as a normal activity**
  - Keep code healthy by improving structure as understanding grows.
  - Don’t let technical debt accumulate unchecked.

- **Professional responsibility**
  - High-quality software is not just a personal preference; it affects users, teammates, and business outcomes.
  - Be accountable for the work you produce.

- **Attention to detail**
  - Naming, design, tests, documentation, and error handling all matter.
  - Small quality improvements compound.

- **Teach and mentor**
  - Craftsmanship is social; skills and standards are shared across teams.
  - Help raise the quality bar for others.

- **Build with discipline**
  - Testing, code reviews, clean architecture, and automation are part of the craft.
  - These are habits, not optional extras.

## The difference between the two

A simple distinction:

- **Pragmatic engineer:** “What is the best solution for this context?”
- **Software craftsman:** “How do I produce high-quality software as a disciplined practice?”

Pragmatism is about **effective decision-making**.  
Craftsmanship is about **quality of execution and growth of skill**.

## How they fit together

The best engineers usually combine both:

- **Pragmatism without craftsmanship** can lead to fast but messy systems.
- **Craftsmanship without pragmatism** can lead to beautiful but overengineered systems.

Together, they mean:
- ship useful things,
- keep them maintainable,
- apply judgment,
- and improve constantly.

## A concise mindset summary

If I had to reduce both to a few lines:

- **Pragmatic engineering:** deliver value with the right amount of effort and complexity.
- **Software craftsmanship:** do careful, professional, continuously improving work that stands the test of time.
